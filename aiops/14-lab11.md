# Lab 11: Dashboards & Toolsets
Now that data is being polled from your FortiGate by FortiAIOps, and
logs are being forwarded to your FortiAIOps appliance, you can now look
into the dashboards, monitoring, and insight toolsets that FortiAIOps
brings to the table.

Please understand that, although you won't have time to drill down into
every component during this hands-on lab, the goal of this section is to
understand and explore some of the key benefits of FortiAIOps and how it
can be a valuable toolset to include with any SD-WAN, Wireless, and/or
Switching deployment.

## AI Insights Dashboard

AI Insights are one of the core values FortiAIOps brings to the table.
It's where in-depth machine learning occurs, used to make intelligent
recommendations when an issue is detected (breaches SLA).

The real power comes from AIOps being able to analyse every single event
log and determine where an issue exists or not.

If you look at the events logs in a typical 1000-seat deployment that a
FortiGate generates, there's potential during peak times for hundreds of
events per second to occur. There's no way a network administrator can
browse through these events in a timely manner to determine whether
performance issues are being seen. It's more than likely that users will
start complaining before anyone looks into a problem...

During this section, you'll look at how some of the SLAs can be set, and
a dynamic baseline can be created. In addition to reviewing a couple of
scenarios that AIOps is designed to flag as user experience issues.

## SLA Config

FortiAIOps includes numerous performance SLAs, and this number continues
to grow with each new release. These SLAs are used as baselines to
determine what's normal in an environment. Whilst this is fine for
specific issues, such as someone using the wrong password to access the
Wi-Fi network, you're likely aware that every environment is different.

Because of this, within FortiAIOps, you can tweak some SLA values.

-   If you haven't already, please open a HTTPS browser session to your
    FortiAIOps appliance, <https://10.222.14.XX:14002>, log in using the
    admin credentials (admin/Fortinet123!), and perform the following
    steps.

-   Navigate to **AI Insights \> Configurations \> SLA Config**

You should see the **SLA Configurations > Device Health** page.

![](media/image124.png)

Here you can manually adjust the SLA
triggers for specific metrics. The default values are recommended as the
starting point for any production environment. However, **IF** it was
considered normal that your devices were often sitting at 80% CPU/memory
usage. You can increase this value to a higher point to prevent the
dashboard from being flooded with SLA warning messages.

-   Within the Device Health Page, change the **AP Health \> Memory
    Value** to **10%**.

-   Select the **Apply** button

This will, of course, change the SLA trigger point, meaning that if an
AP is seen to be using over 10% memory, its health status would fall
outside SLA. The results of this change will be shown within the
Impacted SLAs, Impacted Devices, and Wireless Summary Dashboard, which
you'll look into shortly.

![](media/image125.png)

-   Next, navigate to **SLA Configurations \>** **Time to Connect**

Within this section, you can adjust some of the baseline SLA values for
Wired/Wireless clients that are monitored during initial connection to
the network and throughout the time they are connected.

For example, when a Wi-Fi client connects;

-   If they take longer than 1,000ms to associate or authenticate to
    their Wi-Fi Network (SSID), this would be flagged as a user
    experience issue.

-   If they take longer than 300ms to get a response from a DHCP server,
    this would be flagged as a user experience issue

-   If it takes longer than 2,000 ms to resolve a DNS query, this would
    be flagged as a user experience issue. **Note: '**DNS time' is not
    yet supported by FortiOS. However, if a DNS server is not responsive
    at all or an invalid DNS query is made (i.e., trying to reach an
    unresolvable FQDN), this will be flagged.

![](media/image126.png)

-   Next, navigate to **SLA Configurations \>** **Roaming**

Within this section, you can adjust some of the roaming baseline SLA
values for Wireless clients that are monitored throughout the time they
are connected.

-   If they take longer than 55ms to perform an 802.11r-based roam, it
    would be flagged as a user experience issue.

-   If they take longer than 100ms to perform an OKC-based roam, it
    would be flagged as a user experience issue.

-   If they take longer than 100ms to perform a PMKID-based roam, it
    would be flagged as a user experience issue.

The above Time to Connect and Roaming SLAs values are quite relaxed, and
to be honest, if those values are triggered because a client falls
outside the SLA, users would likely notice that it's taking a while to
connect to the network.

### Dynamic Baselines

You may have noticed that within both the **Time to Connect** and
**Roaming** sections, FortiAIOps has an option to enable **Dynamic
Baseline Configuration**.

Dynamic Baselining allows FortiAIOps to learn about the environment by
monitoring the user experience over time. It then creates a baseline for
these use cases, which in turn can help identify user experience issues
before users even notice them.

Unfortunately, dynamic baselining is not something we can validate
during a workshop, as it requires at least a full day's worth of data to
start building a baseline. The more data is available, the better the
baseline quality, due to the increased number of data points. However,
understanding how this works is key as it's a true benefit.

-   Navigate back to **SLA Configurations \>** **Time to Connect** and
    set the following;

-   Dynamic Baseline Configuration: **Enable**

-   Scope: **FortiGate** -- Baselines can be built on a per Group, per FortiGate, or AP basis

    ![](media/image127.png)

-   Time Selection: **Duration and select 1 Day(s)**(range the baseline
    thresholds will be built upon). Hence, you need at least one day of
    data collection.

-   Schedule Baselines Computation: **Enter tomorrow's date and the hour
    marker (e.g., 10 for 10:00 AM),** ideally 24 hours beyond the
    current time. (You are setting what date and hour to run the
    baselining algorithm).

-   Repeat Cycle: **1 Day(s)** How often do re-run the baseline

-   Select the **Apply** button

Once the baseline algorithm has been run,
the baseline values calculated
by FortiAIOps are displayed in the table, as shown below.

As shown in the table above, the association, authentication, and DHCP
response times are significantly lower than the default/manual
baselines. This baseline was calculated on a Per AP basis.

For example, for AP S/N: FP231GTF22000080, if an association takes
longer than 2milli-seconds, this would be flagged as a user-experience
issue as it's outside the normal boundaries expected for this AP.

-   Navigate back to **SLA Configurations \>** **Roaming** and set the

-   Dynamic Baseline Configuration: **Enable**

-   Scope: **SSID** - Baselines can be built on a per Group, per

-   Time Selection: **Duration and select 1 Day(s)**(range the baseline

-   Schedule Baselines Computation: **Enter tomorrow's date and the hour
    marker (e.g., 1 for 1:00 AM), ideally 24 hours beyond the current
    time**. (The date and hour to run the baselining algorithm).

-   Repeat Cycle: **1 Day(s)** How often do re-run the baseline

-   Select the **Apply** button

Once the baseline algorithm has been run,

![](media/image130.png)
the baseline value/s calculated by FortiAIOps are displayed in the
table. You can recompute specific baseline values as per the image

You can see in the table above that the 11r roaming and OKC roaming

It's a report that should be included with every FortiCare ticket logged
where a FortiGate, Managed FortiAP, and/or managed FortiSwitch is
involved.

### Spectrum Analysis

All currently supported FortiGate Managed APs can function as a Wi-Fi
spectrum analyzer on the bands for which their radios are capable of
operating.

This can help identify wireless user experience issues caused by
non-Wi-Fi interference, which is becoming increasingly common,
especially in the green energy and energy-saving sectors.

More entities are transitioning to energy-star-rated offerings, such as
smart homes and smart buildings, to reduce their energy costs.
Structures with higher energy-star ratings often have mandatory
energy-saving devices that can and do interfere with wireless networks.

Many customers' Wi-Fi networks, including several Fortinet offices
worldwide, have fallen victim to energy-saving devices that have
directly impacted wireless deployments.

The most common cause of these issues is the use of motion sensors,
which can activate and deactivate lighting.
[Example](https://www.dropbox.com/scl/fi/xtb3trmy3cmj5dp5bzgud/DET150.pdf?rlkey=1d9atkqj40wgrq83mtlsw8p5k&dl=0)

These devices typically operate

![](media/image151.jpeg) within the UNII-3 band,
primarily around 5.8 GHz, but also cross into the 5.7 GHz and 5.9 GHz
ranges. Hence, this means typically that CH149-165 are unusable where
these devices have been deployed. The image below contains an example of
what you may see if using an Ekahau Sidekick as a spectrum analyzer in
the same space.

Now, if you have a Spectrum Analyzer available, such as an Ekahau Side
Kick, you would see something similar to the image below, highlighting a
continuous transmitter nearby.

However, as most customers don't have high-end Wi-Fi troubleshooting
hardware on hand, using the Spectrum Analyzer capability built into
FortiAP/FortiAIOps can also help identify if there's an RF problem.

Note: The signal interference doesn't need to be relatively loud, just
persistent. That's all it takes. However, in your lab environment, it's
very easy to see why the 2.4GHz band isn't ideal to use.

### Rogue APs

Within FortiAIOps, navigate to **Wireless \> Rogue APs**

![](media/image160.png)

-   If a rogue AP is shown as online, this means it's currently
    broadcasting within the vicinity of your APs

-   If the Signal Interference, i.e., RSSI of the Rogue, is \> 75 dBm,
    it will likely be within 10m of your APs.

-   If detected by 3 or more APs, you should be able to locate the
    device within your environment. FortiAIOps will list the 3 APs that
    can hear the rogue at the highest RSSI.

-   If the device is seen Off-wire, that means it's not connected or
    seen on the wired side of the network. This identification method
    uses the AP base MAC address. If the Ethernet MAC is visible on the
    wired side and aligns with the radio MAC on the wireless side, it
    would be flagged as on-wire.

-   What's a Rogue in the Wi-Fi sense? If you believe it's a malicious
    Wi-Fi device, sorry, you're misinformed.

-   Even Google AI provides the misinformed answer, i.e., you can search
    What is a Rogue access point and get this bogus response: "A rogue
    access point is **a wireless access point that has been installed on
    a secure network** without explicit authorization from a local
    network administrator." Yes, this does fall into the definition of a
    rogue, but it's not entirely correct.

-   A rogue is **any interfering Wi-Fi-enabled device seen by your
    managed access points;** this could be a station or access point.
    This can be as simple as a neighbouring AP that's not part of your
    managed network, and nothing more than that. It doesn't need to be
    malicious or connected to your network to be considered a rogue.

-   Rogue APs and clients can harm Wi-Fi performance. However, 802.11,
    being a contention-based standard, does a great job of sharing the
    airtime with neighboring devices on the same channels (so long as
    they can hear each other).

-   Meaning two or more APs, on the same channel and channel width, will
    indeed share the channel airtime as equally as possible. Where
    things can and often do go wrong is when an Access Point (AP) is
    configured to operate using 40MHz or 80MHz wide channels, while at
    the same time the neighbouring APs are set to run on 20MHz wide
    channels, resulting in overlapping Basic Service Set (BSS) issues,
    also known as Wi-Fi death for the APs running on the wider channels.
    (No, this is not going to be a lesson around OBSS).

-   However, it's highly recommended to identify rogue access points
    and, where possible, configure your Wi-Fi network to a point where
    these rogue APs will have as minimal impact. FortiAIOps enables this
    by displaying all current rogue APs detected by all managed APs
    across all FortiGates from a single central location.

-   When combined with the Wireless Heatmaps and Wireless Location
    Services engine available within FortiAIOps, you can also
    triangulate and see where rogue devices are in your environment to
    remove them should it be necessary.

#### Cable Test

The Cable test is a diagnostic and troubleshooting tool that allows you
to check the state of cable pairs between the FortiSwitch and the
devices connected to its physical copper ports. This tool does not work
on fiber ports and may provide some inaccuracy for very short ( <1m ) or
very long cable runs ( >100m ).

### Statistics

Within the Statistics tab, you can view all SwitchPort Ethernet frame
metrics. This can be used to identify connectivity and performance
issues on Ethernet links. For example, if you are seeing TX, RX, or CRC

### Wired Clients

-   Within FortiAIOps, navigate to **Switch \> Wired Clients**

From this Dashboard, you can monitor the wired clients seen by the
FortiSwitches that are deployed in your network. This page displays a
graphical snapshot of client activity, including the total number of
FortiSwitch clients, their status (online or offline), client device
details, and associated VLANs. Hovering over the charts provides
specific statistics, and clicking on a specific area on the chart
filters the data displayed on this page.

![](media/image165.png)

A great use case for this dashboard is identifying which switchport a
client is connected to on the network at a specific point in time.
Recently, a customer in Australia used this dashboard to locate a
malicious botnet client in their network. The MAC address appeared to be
spoofed, and all they had was the device name to go from. Without
FortiAIOps, they don't believe they could have isolated the client as
quickly as they did.

## SD-WAN Dashboards

The SD-WAN Dashboards provide insights into the monitored SD-WAN
interfaces. Using machine learning and AI modelling, this dashboard will
show when an interface is or has been impacted and predict when further
impacts may occur.

The SD-WAN dashboard has been significantly improved within FortiAIOps
3.0; Improvements include

-   Monitoring/Dashboard improvements

-   AI-Driven Predictive Modelling and Anomaly Detection (Forecasting)

-   Dynamic Baselining Model of Normal Network Behaviour (Dynamic SLA
    baseline)

-   Deviation Analysis for Proactive Anomaly Detection

-   Many new SLAs to improve WAN alerting and performance, with the
    ultimate goal of improving WAN reliability and user experience.

### Insights Dashboard

-   Within FortiAIOps, navigate to **SD-WAN > Insights**

    ![](media/image166.png)

-   In the top menu bar, under FortiGate, ensure your lab **FGT-WLC** is
    selected and that your SD-WAN interface **port5** is selected

-   Then select the **Apply** button

The Insight Dashboard displays current and historical SD-WAN performance
metrics, which can be traced back 24 months, provided the data is
available within FortiOps. This can be used to examine SD-WAN link
performance and utilization statistics over time. For example, to
determine if and when more bandwidth may be needed.

![](media/image167.png)

**Note:** To obtain all the metrics shown in this dashboard, all SD-WAN
configurations must be in place as per Lab Section 9, along with
Application monitoring and traffic logging being enabled on the relevant
outbound firewall policies.

Several of these widgets, such as Performance Status, can also be
drilled down into to gain further insights related to the displayed
data, including reviewing individual performance results for each SD-WAN
SLA, as shown in the image below.

![](media/image168.png)

Looking at the SD-WAN Insights dashboard, you will also notice the MOS
Score or Mean Optimisation Score. A MOS is a numerical measure of the
human-judged overall quality of an event or experience. In SD-WAN, a
Mean Opinion Score is a ranking of the quality of voice and video
sessions.

MOS is judged on a scale of 1 (bad) to 5 (excellent), and is the average
of a number of what would typically be human-scored individual
parameters. Within FortiAIOps, the MOS is generated by an Objective
Measurement Method that approximates a human ranking based on
performance metrics observed over time. For this to be accurate, your
SD-WAN baselines must be accurate. Therefore, it's essential to check
your SD-WAN performance monitors and ensure the threshold values set for
the following are at a level that should always be within the SLA,
unless there is a real performance issue.

-   Latency Threshold

-   Jitter Threshold

-   Packet Loss Threshold
